# Worker-side Git quarantine verification

`verifyGitQuarantine` is internal acquisition-worker plumbing. It is not a host API or a qualified-store constructor. Every Git command it runs parses untrusted objects and must execute inside the measured acquisition unit with aggregate CPU, memory, process, filesystem, disk, inode and wall-time enforcement. The direct tests use small trusted synthetic repositories and establish algorithm behavior only.

The worker receives exact snapshot IDs and trusted acquisition bounds. Defaults cap 16,000 objects, 8,000 commits, 32,000 filesystem entries, 32 MiB per object, 256 MiB expanded object data and 128 MiB of repository files. Lower positive bounds are permitted. Metadata and graph command output also have a 2-MiB ceiling. These checks supplement the unit's resource boundary. They cannot replace it, since the Git parser runs before the verifier can inspect its output.

The staging repository uses a fixed sparse bare configuration with hooks, fsmonitor, commit graph and multi-pack-index disabled. It has exact `refs/sfl/head` and `refs/sfl/base` values and a detached `HEAD` matching the captured head. Unknown metadata/configuration, shallow boundaries, alternate stores, grafts, replacement refs, promisor files, symlinks and hardlinks are refused. Only the expected metadata, loose objects and pack/index/reverse-index paths are permitted. Directory enumeration is incremental and bounded; the verifier never follows a repository symlink.

Verification counts the complete physical object inventory, including unreachable objects, checks object types and expanded sizes, and runs full strict fsck with no configured severity overrides. Both tips must be commit objects; the declared merge base must be a commit or absent. A complete parent traversal of both tips must contain every referenced parent. `merge-base --all` must return exactly the declared unique merge base. Read-only commands retain the existing explicit no-replacement and no-lazy-fetch flags. Missing history is refusal, never shallow confidence or an automatic fetch.

Once every other check has passed, the history of both tips is complete and verified, so Git's definite answer about it is a typed [permanent refusal](SNAPSHOT-EVIDENCE.md#permanent-refusals) for this snapshot. A declared merge base absent from that history, or `merge-base` exit 1 for tips that share no ancestor, is `missing_history`. A complete answer that differs or names several merge bases, or more than its bounded output holds, is `ambiguous_history`. The worker exports it as a [refusal record](GIT-MATERIALIZATION.md#capture-refusal-record). A declared merge base of another object type, a failed fsck or traversal, a killed command and cancellation stay opaque verification failures.

An object, commit or byte bound overrun is also a definite answer about the fetched history, so it is the permanent `history_limit` refusal. The fetch keeps every pack (`fetch.unpackLimit=1`) and completed, so index-pack has verified each pack and the store holds exactly the history the tips need. Each bound is checked where it is measured, and verification stops there without running Git on the rest:

- Repository files over the disk-byte bound. Enumeration still checks the whole layout, and the fixed metadata files must match, so only an otherwise valid repository overruns.
- More objects or commits than their bounds, an object over the object-byte bound, or a total over the expanded-byte bound. Every inventory line must be well-formed and unique, including lines after the overrun.
- An inventory over its 2-MiB output ceiling. Only the exact output prefix that fit is kept, and its complete lines must be well-formed and themselves overrun a bound. Even the longest well-formed line within the object-byte bound fits more than 25,000 times in that prefix, above the largest object bound, so honest Git output always does. A prefix without an overrun stays opaque.
- A parent graph over its 2-MiB output ceiling, after strict fsck and the commit bound have passed.

The filesystem entry bound stays opaque, as do invalid bounds. With every pack kept, an honest fetch has a few fixed paths and one pack, so too many entries never describe the history. Wall-clock limits are never definite answers either: the host acquisition run's two-minute phase, the source guest's 110-second worker deadline, the host's 150-second source VM run phase and every other cancellation leave verification opaque, as do the unit's memory, task and CPU limits, which kill a command rather than let it answer. A history too large to fetch within those limits therefore stays a transient failure, which the [poll loop](POLLING.md#transient-capture-failures) retries with a per-request backoff without blocking other PRs. A refusal is per snapshot, so a later change of the configured bounds does not reopen an already refused request; a new head or a fresh request is captured again.

Only a bounded inventory receipt returns on success. It binds the snapshot and sorted object identities/types/sizes and records counts and byte totals. Every failure returns a zero inventory with a fixed error. There is no partial qualified result, network operation, credential access, candidate checkout, hook execution or publication capability.

Tests use the installed Git producer with actual packs, indexes and reverse indexes. Complete SHA-1 and SHA-256 repositories pass. Corrupt packs and every listed metadata escape route fail. Separate fixtures exceed each configured bound and cancel input; each object, commit and byte overrun is `history_limit`, through direct verification and through the actual worker fetch and export, and the filesystem entry bound and cancellation stay opaque. Real histories over the default commit, object, object-byte, metadata-output and parent-graph-output bounds are each measured independently and refused as `history_limit`. The metadata parser refuses only well-formed complete lines. Another fixture has present head, base and merge-base commits but a missing older parent; it returns no qualified inventory. The strict checker also rejected an initial fixture whose symbolic HEAD pointed outside `refs/heads`, so the producer now writes the exact detached head instead of weakening fsck.

The [concrete source factory](GIT-FACTORY.md) composes fresh quarantine, measured runtime pins, in-unit fetch/verification/capture/export, private input/output bindings and stopped-unit/broker checks. The [service assembly](GIT-SERVICE.md) owns this path. These are implemented source mechanisms; the complete protected launch and aggregate physical/resource/recovery qualification remain unproved. Host-side `CaptureSnapshotEvidence` or `GitStore.command` against downloaded pack files would leave an unconstrained parser gap even after worker verification. A bounded plain-object materialization, or a separately protected concrete reader, must close that gap. Neither this inventory nor the direct algorithm tests establish protected-unit qualification, a production immutable store, App eligibility or activation authority.

The [worker export and sealed reader](GIT-MATERIALIZATION.md) now materialize
bounded plain blobs and restore the packet without host-side Git parsing.
The factory keeps them private staging until its authenticated worker and
whole-unit/broker stop checks pass. Its [retained export archive](GIT-EXPORT-ARCHIVE.md)
and recovery source preserve those bindings across reopening. Neither the
algorithm tests nor those source mechanisms qualify aggregate physical shutdown
or arbitrary host-crash recovery.
